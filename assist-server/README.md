# Ferry Assist server

A small standalone Node/Express sidecar, separate from the core Tauri/Rust
app on purpose: it keeps every credential that would be dangerous to embed
in a distributed desktop binary (B2 master key, sponsor-tech API keys) on a
server Ferry controls, never inside the app itself.

Two kinds of feature live here:

**Core (Rust calls this directly, not gated by any frontend flag):**
Ferry Cloud Backup — see below. This is what "free, managed cloud storage"
actually means: the desktop app never holds Ferry's real B2 credentials, so
this sidecar (or wherever it's deployed for real use) has to be running for
Cloud Backup to work at all.

**Optional hackathon sponsor-tech features (frontend-gated by
`VITE_ASSIST_SERVER_URL`, off if unset):**

1. **AI migration assist** — for apps the reinstall picker couldn't match to
   a confident source (Tier 2/3), get a plain-language explanation and,
   where safe, a suggested install command — generated by an open model
   running on **Nosana**'s decentralized GPU network, then dry-run **inside
   a Daytona sandbox** before it's ever shown as trustworthy. Nothing
   AI-suggested touches the user's real machine until it's been tested
   somewhere disposable.
2. **Cloud Backup share links** — after upload, provision a real `https://`
   subdomain via **DNSimple** that shows a simple backup status page,
   instead of handing the user a raw ID.

## Ferry Cloud Backup (managed, free-to-user)

The desktop app never touches Ferry's real B2 account. For every backup,
`services/b2admin.ts` asks B2 to mint a **brand-new, disposable Application
Key** — scoped to one bucket, one `namePrefix` (`<backupId>/`), one
capability (`writeFiles` for upload, `readFiles` for restore), and a short
lifetime (6h / 30min). The desktop app then authorizes with *that* key
directly against B2 for the actual file transfer, so this server's bandwidth
is never in the path for the bytes themselves — only the small "mint me a
key" round trip is. After a successful restore, the desktop app asks this
server to delete that backup's files.

### Setup

1. Create a Backblaze B2 account and a bucket (any name).
2. Get the account's **Master Application Key** ID + secret from the B2
   dashboard's App Keys page — not a bucket-restricted key, since minting
   new keys (`b2_create_key`) needs the `writeKeys` capability, which only
   the master key (or an equivalent custom key) has.
3. Set `B2_MASTER_KEY_ID`, `B2_MASTER_APPLICATION_KEY`, `B2_BUCKET_NAME` in
   `.env`. **This key must never go into the desktop app or get committed
   anywhere** — it lives only in this server's environment.

## Setup

```bash
cd assist-server
npm install
cp .env.example .env
```

### Daytona

1. Create an API key at <https://app.daytona.io/dashboard/keys>.
2. Set `DAYTONA_API_KEY` in `.env`.

### Nosana

Nosana's documented way to run a hosted inference endpoint is to deploy a
model template from their dashboard (it generates the job definition JSON
for you — the exact Docker image/port schema isn't something to hand-write,
since it changes with their templates). Steps:

1. On the Nosana dashboard, pick an LLM inference template (e.g. an
   Ollama/vLLM-based one) and deploy it to a market you have NOS + SOL
   funded for.
2. Export/copy that job's definition JSON and save it as
   `assist-server/nosana-job-definition.json`.
3. Set `NOSANA_MARKET` to the market address you deployed to, in `.env`.
4. Make sure the `nosana` CLI is installed and on `PATH` (`npm i -g
   @nosana/cli` or see their docs) — this server shells out to
   `nosana job post` rather than depend on a specific SDK method signature,
   since the CLI is what Nosana's own docs treat as stable.

The first request to `/api/assist/suggest` will trigger a job deploy and
block until Nosana reports the endpoint is up; after that the endpoint URL
is cached for the life of this process.

### DNSimple

1. Generate an API access token in your DNSimple account, and note your
   numeric account ID (`GET /v2/whoami`).
2. Pick a domain already in that account (`DNSIMPLE_DOMAIN`).
3. **Provision a wildcard TLS certificate for `*.DNSIMPLE_DOMAIN` once,
   ahead of time**, via DNSimple's Let's Encrypt automation (dashboard or
   `POST /v2/:account/certificates`). We don't request a fresh cert per
   share link — DNS-01 propagation takes minutes, which isn't demo-friendly
   — we just create an A/CNAME record per backup and let the existing
   wildcard cert cover it.
4. Set `PUBLIC_HOST` to wherever this server is actually reachable from the
   internet (an IP for an A record, or a hostname for a CNAME — set
   `DNSIMPLE_RECORD_TYPE` accordingly). For a local demo this typically
   means running this server behind a tunnel (ngrok, Cloudflare Tunnel,
   etc.) and pointing `PUBLIC_HOST` at that.

## Run

```bash
npm run dev
```

Defaults to `http://localhost:8787`. The Rust side finds it via
`FERRY_ASSIST_SERVER_URL` (defaults to `http://localhost:8787` if unset —
fine for local dev, but a real deployment needs this set to wherever the
server actually runs). The optional frontend features are separately gated
by `app/.env`'s `VITE_ASSIST_SERVER_URL` (see `app/.env.example`).

## Endpoints

| Method | Path | Body | Used by |
|---|---|---|---|
| POST | `/api/cloud/upload-key` | — | `cloud/b2.rs` (core, always active) |
| POST | `/api/cloud/download-key` | `{ backupId }` | `cloud/b2.rs` (core, always active) |
| POST | `/api/cloud/delete` | `{ backupId }` | `cloud/b2.rs` (core, always active) |
| POST | `/api/assist/suggest` | `{ apps: {name, publisher, tier}[], targetFamily }` | AppPicker (optional) |
| POST | `/api/assist/verify` | `{ command: string }` | AppPicker (optional) |
| POST | `/api/cloud/share-link` | `{ backupId: string }` | CloudUpload (optional) |
| GET | `/status/:backupId` | — | opened from the share link |

## Honesty note

This is hackathon-scoped: no persistence (status links die on restart), and
**no auth on any endpoint**, including `/api/cloud/upload-key` — anyone who
can reach this server can currently mint an upload key and store data at
Ferry's expense. Fine for a demo behind a local/tunnel URL nobody else knows;
add real auth (even just an API key check) before this is a public endpoint.
Minted keys aren't explicitly revoked early, only left to expire on their own
(6h/30min) — for real usage, `b2_delete_key` after a completed
upload/download would tighten that window further.

Sandbox verification (`services/daytona.ts`) only checks the command's exit
code, not what it actually did inside the sandbox (e.g. it won't catch a
"succeeded but installed the wrong thing" case) — good enough to demo the
never-run-untested-code-on-the-real-PC principle, not a substitute for a
real security review before shipping.
